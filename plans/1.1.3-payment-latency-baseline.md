## 涉及代码及接口

| 位置 | 计划用途 |
| --- | --- |
| `fiber-lsp-client/src/main.rs` | 可选计时开关及结束摘要；不影响默认输出 |
| `src/payments.rs` | bootstrap、send、等待、依赖查询、SDK 校验/确认、release、最终 reconcile 区间 |
| `src/rpc.rs` | 区分 LSP/CKB RPC，统计方法、等待时间、完成时间和错误；不记录 payload |
| `src/store.rs` | 区分序列化/快照复制、文件 fsync、rename、目录 fsync 及写入次数 |
| `../fiber/crates/fiber-lib/src/fiber/{channel,payment}.rs` | 仅在授权范围内增加服务端阶段耗时，区分待签、提交后恢复及最终 Success |
| `fiber-lsp-client/tests/` 与必要的 Rust 测量入口 | 自动组织收付款、采样和汇总；不把控制流程塞进 Shell |
| README / docs/payment-flow.md | 计时开关、指标语义和结果解释 |

CLI 的 `--timings` 按本次用户要求输出中文阶段摘要，收款单独记录首次观察到本发票入账 TLC 前的在线等待和之后的收款处理（包含协议等待），命令运行时间另列；恢复仅统计本次窗口，旧聚合样本不能回推该分界。`--timings-json` 保留完整机器格式；CLI/RPC/store 分项继续使用同一计时数据。examples/latency_baseline.rs 已支持代码传票、同一协调器计时及失败停止；本轮复用，并修正失败计数的诊断。

## 详细技术设计

### 计时口径

| 指标 | 起止点 |
| --- | --- |
| `T_cli_startup` | 外部测量进程启动 CLI 到客户端具备发送条件；内部补报配置/账户恢复耗时 |
| `T_send_rpc` | send_payment 请求开始到收到响应；只代表请求处理，不代表付款完成 |
| `T_payment_success` | 付款服务端接受该 hash 到付款端 Success；在同一个进程用单调时钟记录 |
| `T_receiver_balance` | 同一测试协调器观察付款开始到收款余额变化；记录观察方式和采样误差 |
| `T_payer_complete` / `T_receiver_complete` | 测试协调器开始付款到对应 CLI 完整完成；冷启动/在线稳态分别列出 |
| `T_external_sign` | 取得待签请求到 SDK 校验/签名、重放资料落盘、提交完成的分项；请求 ID 用于关联 |
| `T_chain_check` | 每次原像释放实际使用的独立链上核验 |

CPU 校验、同步落盘、RPC 和等待的区间可能嵌套或并发；保留层级和调用次数，不把所有区间简单相加解释为墙钟总耗时。长轮询的等待另列，不能当作 HTTP 传输开销。

若未获 Fiber 测量代码授权，可先用既有日志与 CLI/RPC 数据报告近似值，明确服务端精确计时缺失，不将轮询观察值冒充精确 Success 时间。

### 对照场景

1. 同机普通 Fiber 的两跳支付：金额、费用、流动性、二进制构建及最终 Success 一致。
2. 同一 LSP 两账户在线支付：收款客户端提前在线，付款方分别使用冷启动 CLI 和测试中复用的 session/driver。后者仅为基准，不引入生产后台进程。
3. 普通节点 hold invoice 场景：单列收款释放动作及完成证据，用来解释自动发票与外部签名收款的语义差异。
4. 活跃付款为 1、已完成历史为 0/10/100/1000 条：模拟历史用于隔离测试 store，不伪造现有运行账户的完成记录。

每个性能场景先预热 5 次，再采集至少 30 次顺序付款；记录全部尝试和失败/超时。p95 的最低样本只用于初步比较，结果不稳定时增加样本。付款前准备流动性，不将开关通道或补款耗时混入支付区间；必要的再平衡另记。

冷启动、租户 runtime 首次唤醒和已在线稳态分组，不把快样本混入慢样本后只报一个平均数。对照使用相同计时选项，并记录计时对总耗时的影响。

### 数据与保密

每条记录包含构建 commit、Release 配置、场景、公开 hash/请求 ID、方向、阶段、单调区间、RPC/写入计数、终态与失败原因类别。

不写 token、root-key、preimage、完整发票、签名正文、完整 RPC 请求/响应。实验记录留在隔离的结果目录，不写入 payments.json/account.json，也不默认保存到仓库。

使用只读 `strace`/系统调用采样交叉检查 fsync 次数时，采样和无采样结果分别报告；采样期间不捕获含秘密的 read/write 缓冲区。

## 实施步骤

1. 固定隔离环境、对照路径、构建标识及指标起止点；检查既有数据与测试目录分离。
2. 增加可选计时及聚合输出，先完成 CLI/RPC/store 测量，再按授权补充服务端阶段计时。
3. 用 Rust 驱动测试场景，等待收款端就绪后发送，按原 hash 观察双方完成，禁止超时后自动再次发送。
4. 采集基线，检查 RPC、签名次数、fsync 数量和耗时能相互解释；记录未测量部分。
5. 在本方案保存基准摘要和结果位置，向 [1.1.2](1.1.2-cli-payment-driver.md) 提供同条件复测入口。

## 产物与验证

产物：可选计时入口、Rust 基准流程、脱敏结果、README 指标说明及后续可复用的测量条件。

验证：检查默认行为/退出码没有变化、统计没有秘密字段；同场景重复采样；比较启用/关闭统计的开销；测试成功、错误和超时都计入次数。所有付款测试使用隔离环境。

满足本级条件：至少有普通 Fiber 与 LSP 对照、冷启动与稳态分组、历史数量实验、分项及失败率。没有可比较的对照时不能宣称 LSP 已达到普通 Fiber 性能。

剩余工作：预热与至少 30 次自动传票样本、普通 Fiber 对照、冷启动/稳态分组、公网 RTT 和计时开销对照、服务端等待阶段分解。
验证结果：CLI 84 项测试及所有 target 的 clippy 通过；新增时间边界测试验证不同 hash/出款 TLC 不启动收款处理、重复签名不重置计时、协议等待仍计入处理、超时不冒充完成。中文摘要已使用用户提供的付款指标离线渲染核对，人工/JSON/默认静默及选项互斥均检查通过，未访问账户；自动基准改用 --timings-json。单笔付款端总耗时下降 13.26%，LSP RPC 次数下降 58.54%，文件写入次数下降 76.77%；文件同步单次变慢使累计同步耗时上升。隔离组合 RPC 测试完整收付款成功；该测试为 Debug/内存 SDK/合成链，只用于正确性，不作为 Release 性能证据。
未验证项：稳定 p50/p95、服务端精确 Success 和余额变化时间；最后的结算去重补丁尚未复测。
恢复点：保持完整完成定义，用现有 Rust 测量入口在隔离环境继续采样；不把这些不同存储时延的单笔对照解释为稳定性能收益。
