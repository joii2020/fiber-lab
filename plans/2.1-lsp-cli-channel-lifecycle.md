## 技术要点

### 职责与可信边界

- CLI 负责命令入口、账户复用、操作意图、`listChannel` 查询输出和恢复调度；Rust 钱包负责独立查询链数据、验证钱包支出、费用和退款并签名。通道查询由独立的 `listChannel` 提供，`status` 不承担本需求。
- SDK 负责客户端 signer、开通条款与合约验证、通道 binding、签名验证及持久化签名历史；LSP RPC 负责远端协调和交易提交。
- `OpeningNetwork` 等可信参数来自本地 Node3 / offckb 配置和独立链查询，不能以 LSP 提案作为可信依据。#5 私钥仅在客户端使用，不传给 LSP、不写日志。
- 复用现有账户锁、恢复流程和 signer store，不重新注册或生成根密钥。金额转换采用整数运算。

### 默认 lock 与两类签名

首版钱包输入与 #5 退款使用 CKB 默认 `secp256k1_blake160_sighash_all` lock。采用 Fiber 当前使用的 `ckb-sdk` 5 系列，在 Rust 客户端读取 #5 私钥，核对派生公钥哈希与完整钱包 lock，使用 `SecpCkbRawKeySigner` / `SecpSighashUnlocker` 完成出资交易的 recoverable ECDSA 签名。

通道 output[0] 仍使用 Fiber `FundingLock`；初始 commitment、后续状态和协作关闭的 MuSig2 签名由 SDK 派生的通道密钥处理，经 `submit_channel_signature` 提交。#5 钱包私钥与 SDK 通道密钥承担不同职责，不相互替代。

### 开通与必要签名

通过 `HostedSession::open_tenant_channel` 和三个应用适配接口取得已验证的冻结交易；钱包独立验证输入归属、可用性、资产、找零、净支出与费用，SDK 验证合约、保留金额、协商条款和 binding。

只签署已验证的冻结交易，保持完整 raw transaction 不变，仅填写对应 lock group 的 witnesses；保存后提交出资，核对返回 hash，再通过 `get_channel_signing_status` / `submit_channel_signature` 推进签名。需要确认的 `ProcessOutcome` 必须对应本地操作意图，不采用测试 agent 的无条件自动批准循环。最终以出资链上确认及 `ChannelReady` 判断开通完成。

本次源码核对的结论是：`open_tenant_channel` → 返回已协作冻结交易及 opening context → 本地默认 lock 签名 → `submit_signed_funding_tx` → SDK 通道签名 → `ChannelReady` 路线有现成服务端支持，当前没有发现需要新增服务端能力的前置。RPC 返回冻结结果需要 Public T 已接受通道；自动接受关闭或金额未达到配置阈值时会等待接受，不能仅凭钱包有余额判断可以完成开通。

### 共用 #5 的支出边界

Node3 公共节点和客户端共用 #5 时，钱包净支出包含双方注入额与整笔交易费，不能只用 CLI 本方 `funding_amount` 作为钱包支出上限。按当前默认配置，本方 1000 CKB 与 Public T 的 99 CKB 合计注入 1099 CKB，另付交易费；本方 1000 CKB 已包含保留金额，不再重复叠加该保留金额。

共用钱包的对方注入额和总支出上限须依据可信本地配置及本地钱包条款明确、在开通请求前保存，并验证冻结提案与之相符；不能直接接受 LSP 返回的对方金额作为额外扣款授权。本次已按 Node3 本地配置中的对方注入额加每笔 1 CKB 费用上限落实并持久化该规则，具体计算与签名设计见 [2.1.1 外部出资与签名](2.1.1-lsp-cli-channel-lifecycle.md#外部出资与签名)。

### 协作关闭与最终状态

仅在通道归属、binding、已验证余额、链上出资及 TLC 状态满足条件时，以 `shutdown_channel(force: false)` 发起协作关闭。钱包依据本地条款独立计算总费用与双方分摊，建立 `CloseAuthorization`，由 SDK `prepare_close` 等流程验证金额及绑定的退款脚本后签名。

关闭 hash 来自包含 closed 通道的列表，最终结果还须独立查询 CKB 交易确认与退款输出。`listChannel` 使用当前账户 tenant token 查询通道，结合服务端状态、链上结果和本地待恢复阶段展示结果，避免将受理或提交误报为完成；查询流程不推进开关通道或提交签名。

### 持久化与恢复

在现有账户目录保留完整开关通道意图、请求参数、channel key / channel ID、冻结及签名交易、交易 hash 和处理阶段；SDK 状态与关键进度在下一次外部操作前落盘。

超时、响应丢失和进程退出后的重试先核对远端与链上状态，再继续原意图。SDK 同请求恢复语义不能直接推广为所有 RPC 的幂等保证；出资、签名和关闭提交分别核对原操作，签名重用 SDK 持久化历史。

## 风险与依赖

- **钱包与网络参数**：已核对 offckb 默认隐藏私钥，`--show-private-keys` 可在客户端子进程内获取 `privkey`；已在 Rust 客户端内存使用 #5 私钥完成链上签名，未打印或持久化私钥。客户端需捕获 stdout / stderr，禁止透传含密钥输出，并核对私钥与完整 #5 默认 lock 一致。`OpeningNetwork` 映射已完成并验证，详见三级。
- **共用钱包扣款**：Public T 与客户端的 #5 输入属于同一个默认 lock group，必须完整分组签名并验证双方注入总额；双方注入额及每笔 1 CKB 费用上限在请求前保存。
- **关闭费用**：交易大小、费用及双方分摊必须独立计算；已选择 1000 shannons/1000 bytes、1 CKB 费用上限和本端承担全部费用的本地规则，不能直接采用 LSP 声称的费用作为授权。
- **恢复一致性**：外部操作成功但本地响应未保存时，必须通过远端 / 链上核对及 SDK 持久化记录恢复；恢复不充分可能重复出资或生成冲突签名。
- **再次开通**：当前服务端保留单通道 opening / 非失败记录，SDK 已有 binding 时拒绝不同开通请求，直接在原租户下创建新通道受限。本方案展示该限制，不清除 binding 或重建账户规避；在线关闭后的重复操作与客户端限制提示已验证。产品要求通过 [一级关闭与查询行为](2-lsp-cli-channel-lifecycle.md#关闭与查询行为) 引用。
- **前置条件**：依赖现有账户、devnet、独立 CKB 查询及本地 SDK / RPC 的实际可用能力，不要求先完成方案 1 的独立验收。本次已获阶段一至四实施授权；在线验证需 CKB 与 LSP 均可用、#5 资金满足出资和保留容量要求。
- **新增必要前置**：本次未发现或新增前置方案；若实施发现 SDK / 服务端缺少必要能力，记录证据、受影响验收条件和恢复点，先准备前置及顺序调整草案，取得开发者明确确认后再调整和实施。

本级作为通道生命周期完整技术范围的 push 和交付验收单位，验收覆盖 [一级 P1—P6](2-lsp-cli-channel-lifecycle.md#产品验收条件)：

1. CLI 完成 SDK / RPC 和 #5 钱包接入，旧账户与配置可复用，开关通道以链上结果及通道最终状态判断成功；`listChannel` 独立完成通道查询与恢复阶段展示，满足一级 P2。
