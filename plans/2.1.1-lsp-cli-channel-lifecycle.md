## 详细技术设计

### 参数与账户复用

命令名称、别名、默认配置、金额单位、首次 / 恢复规则、超时和通道选择均按 [一级产品规则](2-lsp-cli-channel-lifecycle.md#产品需求与范围) 实现。金额由十进制 CKB 字符串以整数运算转换为 shannons，不采用浮点数或隐式出资默认值。

复用现有账户锁、恢复流程、SDK signer store 和 session；兼容已有账户文件，不重新注册或生成根密钥。Node3 / offckb 配置与独立链查询提供 CKB RPC、合约部署、出资 lock、cell deps 及 SDK `OpeningNetwork` 参数，不能从 LSP 提案建立可信配置。

钱包由 Rust 实现，读取 #5 账户信息并在客户端签名；输入和退款使用默认 `secp256k1_blake160_sighash_all` lock，私钥不传给 LSP，也不写入日志。签名依赖采用 Fiber 当前使用的 `ckb-sdk` 5 系列及兼容的 `ckb-types` 1 系列，具体设计如下。

### 外部出资与签名

1. **钱包材料**：从 `offckb --json accounts` 取得 #5 的完整 `lockScript`，核对默认 lock 的 code hash、hash type 与 20 字节 args；需要签名时在 Rust 子进程中调用 `offckb --json accounts --show-private-keys`，捕获 stdout / stderr，只选取 #5 的 `privkey` 并在内存使用，禁止透传含密钥输出或把账户列表写入日志。核对派生压缩公钥的 blake160 与 args 一致；实现已在客户端内存中读取私钥并验证归属，未打印或保存私钥。
2. **三个脚本职责**：RPC 的 `funding_lock_script` 指向 #5 钱包输入锁，`shutdown_script` 指向 #5 退款锁；交易 output[0] 与 SDK `OpeningNetwork.funding_lock` 对应 Fiber 通道 `FundingLock`。后者以通道密钥生成参数，不能替换为默认 CKB lock。
3. **依赖与参数**：默认 lock dep 由服务端 `DefaultCellDepResolver` 从 genesis 解析，`funding_lock_script_cell_deps` 首版不额外提供自定义依赖；客户端独立核对返回交易中默认 lock dep（出资只花默认 lock inputs，不要求 FundingLock 的解锁 deps）。`public: false`、目标 LSP 公钥、SDK `external_channel_signer`、本地选定的 commitment delay / fee rate 均须保存；`funding_fee_rate` 显式选择并保存。
4. **出资额与保留金额**：CKB 请求的 `funding_amount` 是本方总注入额，包含本方 reserved CKB；服务端 `get_funding_and_reserved_amount` 先扣除 reserve 得到可用余额，opening context 又将 reserve 加回。默认 lock 的当前 reserve 为 98 CKB 占用容量加 1 CKB 关闭预留，客户端依可信网络参数计算并与 SDK 结果核对；不能把 reserve 重复加到 CLI 金额上。
5. **接受条件与共用钱包**：Public T 的自动接受是否启用、接受阈值及对方总注入额取自实际本地配置；当前默认阈值为 100 CKB、对方注入为 99 CKB。Node3 与客户端共用 #5 时，先保存本方总额 `A`、可信配置中的对方总额 `R` 及钱包总支出 / 费用上限，再请求开通；本次执行按本地 Node3 对方注入额授权，总支出上限为双方总注入额加 1 CKB 费用上限。冻结交易应满足 `output[0].capacity = A + R`，#5 净支出为全部 #5 输入容量减其普通找零容量，等于 `A + R + 整笔交易费`。示例 `A = 1000 CKB` 时为 `1099 CKB + 交易费`；服务端返回的 `R` 必须与已保存条款一致，不直接用它授权额外扣款。
6. **独立钱包验证**：通过可信 CKB RPC 解析冻结交易的每个 input，核对 live cell、完整 lock、资产及容量，核对通道输出、所有找零、双方注入额和费用。`FundingVerifier` 返回按交易顺序排列的全部已核验 input outpoints，而非仅本方最初选择的子集；SDK `derive_funding_binding` 对完整输入列表作精确比较。
7. **出资交易签名**：按完整 input lock script 建立 `ScriptGroup`；共用 #5 时本方与 Public T 加入的输入属于同一组，必须包含该组全部 input indices。使用 `SecpCkbRawKeySigner` / `SecpSighashUnlocker` 或等价的默认 sighash 过程，生成 65 字节 recoverable ECDSA 签名并写入组内首个 input 的 `WitnessArgs.lock`，保留已有 witness 的其余字段及其他组内容。签名前后比较完整 raw transaction 字节与 tx hash，确保只有 witnesses 变化；先保存签名交易，再调用 `submit_signed_funding_tx`。
8. **通道签名**：钱包签名不完成通道生命周期。后续通过 `get_channel_signing_status` 获取请求，SDK 使用独立的通道密钥验证并生成 MuSig2 签名，经 `submit_channel_signature` 推进初始 commitment、通道状态及协作关闭；仍须等待出资确认和 `ChannelReady`。

源码支持以上首次开通路径：LSP runtime 已注册租户与 Public T 的进程内连接，交易协作冻结后返回 opening result，提交签名交易后恢复通道签名流程。自动接受关闭、金额未达阈值或对端尚未接受时，开通会等待接受；保留原意图并展示原因，不自动改配置或把 RPC 超时当作已终止。

### 独立通道查询

在 CLI 中显式注册名称为 `listChannel` 的子命令，复用 `--config` 和现有账户恢复入口，以当前账户 tenant token 调用 `list_channels`，查询开通中、活动及已关闭通道，再结合本地意图和必要的独立链查询展示结果。输出内容及空列表行为依据 [一级关闭与查询行为](2-lsp-cli-channel-lifecycle.md#关闭与查询行为)。

查询只读取通道与本地恢复记录，不恢复执行开关通道流程或提交签名；本需求不通过 `status` 完成。

### 持久化数据与外部操作顺序

在 `.state/fiber-lsp-client/default/` 保存完整开关通道意图、原始请求参数、channel key / channel ID、冻结交易、签名交易、交易 hash、处理阶段和 SDK 状态；原账户、signer 与交易历史保留。

关键顺序为：保存本地意图 / SDK 状态 → 发起对应外部操作 → 核对并保存结果 → 推进下一阶段。出资交易先验证再签名，签名交易先保存再提交。持久化失败时停止推进。

恢复先核对服务端 pending / active / closed 通道及 CKB 交易状态，再决定是否重发出资、签名或关闭请求。SDK 同请求重试仅用于其已有恢复语义；重复签名使用 SDK 持久化历史，不生成冲突签名。

### 开通与关闭流程

开通依次经过账户 / 原意图核对、SDK 开通与独立钱包验证、冻结交易签名和出资提交、必要通道签名、链上确认与 `ChannelReady`。三个适配接口为 `TenantOpeningRpc`、`FundingVerifier`、`OpeningPersistence`，具体调用步骤见阶段二。

关闭先核对归属、binding、余额、链上出资与未结算 TLC，再保存意图并请求协作关闭；钱包独立计算费用和分摊，以本地条款建立 `CloseAuthorization`，通过 SDK `prepare_close` 等核验后签名。最终核对关闭交易确认及 #5 退款输出，具体调用步骤见阶段三。

### 已落实的配置、费用和恢复边界

1. Node3 的 `ckb.rpc_url` 提供独立链查询；`fiber.scripts` 提供 FundingLock / CommitmentLock 及 deps；链 spec 的 `params.epoch_duration_target` 转为毫秒；CKB genesis 提供默认 lock dep 并保存 genesis hash。commitment 交易 deps 数取 FundingLock deps 数，保留费用采用协议的 1 CKB。只支持 `ckb_dev`。
2. 出资额包含保留金额，默认最低保留额 99 CKB。对方注入额 / 自动接受阈值取本地配置（缺省 99 / 100 CKB），在请求前保存。出资、commitment、关闭费率均显式选用 1000 shannons/1000 bytes，每笔钱包费用上限 1 CKB，commitment delay 为一个 epoch。
3. CKB 关闭交易构造为 FundingLock deps、一个通道 input、双方两个退款 outputs、112 字节最终 witness。依本地脚本和 deps 数构造同大小交易，费用按 `rate * size / 1000` 整数计算；本端作为发起方承担全部费用，自动接受方为零。SDK 与钱包各自核验分摊、完整退款输出及余额；不采用 LSP 声称的费用授权。
4. `channel.json` 格式版本 1 保存原请求、可信 Terms、冻结 / 签名交易、hash、实际出资费、关闭授权及当前签名 request / response；`account.json` 和 SDK signer 快照沿用原格式。阶段为 Opening → FundingSaved → FundingSubmitted → Ready → CloseRequested → Closing → Closed。冻结响应先存，再让 SDK 安装 binding；签名记录与完整请求先存，再提交。保存失败停止推进。
5. 恢复合并 `list_channels(include_closed: true)` 与 `list_channels(only_pending: true)`，包括已删 actor 的失败记录；出资仅在远端仍等待外部出资且 CKB 为 `unknown` 时重发原交易，pending / proposed / committed 不重复提交，rejected 停止。原签名的 request ID 与完整内容一致才复用；SDK 持久化历史保护响应保存前中断的情况。关闭恢复先查询，ShuttingDown 不重新发 shutdown，Closed 验证链上退款。
6. `ProcessOutcome::NeedConfirmation` 只有匹配本地意图才确认：开通仅允许第 1 版 commitment，双方金额固定且无 TLC；关闭只允许独立核验的协作关闭交易。拒绝后续支付、revocation、announcement 和 watchtower 签名。
7. 共用 #5 的首次资金协作需要两个可独立收集的 live cells。开通预检容量和 cell 数，不自动拆分或清理；开发环境的显式 Rust 检查可拆分单个大额 cell 后等待确认。本次在线验证已按此准备，费用 1000 shannons，资金仍归 #5，所有旧记录保留。

余额不足、保留容量不满足、参数不一致、错误交易 / 退款、费用超限、归属不符、状态过期或有未结算 TLC 时明确报错并保留原记录。超时和中断输出当前阶段及恢复命令，不报告操作完成。

## 实施步骤

本次按已授权的阶段一 → 二 → 三 → 四执行。每个阶段结束时记录实际产物、验证结果和恢复点，同步 `2.1` 的交付进度；阶段内继续工作不逐步请求开发者验收。

### 阶段一：账户复用、配置与持久化

1. 复用现有账户锁、恢复流程和 SDK signer store，提供通道命令所需的 session 操作入口，兼容已有账户文件，不重新注册或生成根密钥。
2. 从现有 Node3 / offckb 配置取得 CKB RPC、合约部署、出资 lock 与必要 cell deps；SDK `OpeningNetwork` 所需参数来自可信本地配置与独立链查询，不采用 LSP 返回值作为可信依据。
3. 按“外部出资与签名”实现 Rust 默认 lock 钱包验证和分组签名，复用 offckb #5；读取完整脚本与本地私钥，保留两类签名的职责，不把复杂逻辑放进 Shell。
4. 实现上述意图及阶段记录，SDK 状态和关键进度在发起下一次外部操作前落盘。

产物与恢复点：账户 / session 入口、可信网络配置、钱包接入及持久化结构；验证旧账户恢复后，从已保存原意图进入阶段二。

### 阶段二：开通道与必要签名处理

1. 核对账户注册完成、已保存 LSP 公钥、租户 pending / active 通道和本地意图，决定开始或恢复。
2. 创建并保存本地开通道意图和 pending signer，通过 `HostedSession::open_tenant_channel` 请求私有通道。出资 lock 与 shutdown script 使用 #5 默认 lock；核对 Public T 接受条件，保存双方总注入额、钱包支出边界、费用及 commitment delay 等参数。
3. 独立从 CKB 查询全部输入 cells，验证归属、可用性、资产、找零、共用 #5 的钱包总支出和费用边界，按顺序返回全部 input outpoints；由 SDK 验证通道 `FundingLock`、保留金额、协商条款和通道绑定。余额不足或保留容量不满足时明确报错。
4. 按完整默认 lock group 签署已验证的冻结交易，仅修改 witnesses，保持完整 raw transaction 和 tx hash 不变；先保存签名交易，再调用 `submit_signed_funding_tx`，保存返回 hash 并与本地交易核对。
5. 查询 `get_channel_signing_status`，经 SDK 解码、核验和持久化后调用 `submit_channel_signature`。根据本地操作意图处理需要确认的 `ProcessOutcome`，不得照搬测试 agent 的无条件自动批准循环。
6. 等待出资交易确认及 `ChannelReady`，输出 channel ID、实际出资和交易 hash。RPC 受理或交易已提交不能算开通成功。

产物与恢复点：完整开通命令、必要签名处理及可恢复开通记录；确认通道可用后进入阶段三，中断时先核对原出资与签名结果再恢复本阶段。

### 阶段三：协作关闭与通道查询

1. 核对通道归属、SDK binding、本地已验证余额与链上出资；开通未完成、状态过期或存在未结算 TLC 时拒绝开始协作关闭，并说明原因。
2. 使用开通时绑定的 shutdown script 退款到 #5；明确关闭费率及钱包允许的费用上限，先保存关闭意图，再调用 `shutdown_channel(force: false)`。
3. 独立计算关闭交易大小、费用和双方费用分摊，以本地条款建立 SDK `CloseAuthorization`，验证双方最终金额和退款脚本后签名；不能直接将 LSP 声称的费用作为授权。超限或条款不一致时报错。
4. 使用阶段二的签名处理流程推进关闭；查询包含 closed 通道的列表，取得关闭交易 hash，再从 CKB 验证交易确认和预期退款输出。只有链上结果与本地条款一致才报告完成。
5. 重复执行已在关闭中的操作时先查询状态、继续原签名流程，不新建关闭意图。关闭后保留账户、通道密钥、交易和恢复历史。
6. 验证当前服务端和 SDK 的单通道限制提示，关闭后保留旧记录并明确展示再次开通受限，不清除旧 binding 或自动创建新账户规避。
7. 实现独立 `listChannel` 的通道、余额、交易标识及本地恢复阶段展示，对照远端和链上结果输出最终状态；验证查询不推进操作，本需求不通过 `status` 完成。

产物与恢复点：协作关闭命令、独立 `listChannel` 查询与关闭记录；保留关闭 hash、退款核对结果及再开通限制结论，进入阶段四。

### 阶段四：恢复验证、在线验收与文档

1. 验证网络超时、响应丢失或进程退出后，先核对服务端 pending / active / closed 通道和 CKB 交易状态，再继续同一意图；不把“未收到响应”等同于“未执行”。
2. 验证出资提交、签名提交和 shutdown 的状态核对及必要重发，签名响应重复使用 SDK 持久化历史，不生成冲突签名。
