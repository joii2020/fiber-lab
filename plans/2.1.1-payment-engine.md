## 详细技术设计

### 1. 已实现的收付款及恢复设计

payments.json 版本化，账户 / 通道归属绑定；每笔记录保存方向、hash、amount、max_fee、SDK PaymentAuthorization、invoice、preimage（收款）、创建及发送提交标记、远端原始状态、更新时间、本地完成证据。所有写入受账户锁保护，秘密文件 600。

先写本地意图再写 SDK 授权，再发网络请求。重启重放相同 SDK 授权；不可替换条款。发送提交标记落盘后只查询恢复；新发送只限尚未提交的原意图。创建按原 hash 核对响应并本地重新解析 invoice_address，验证 hash、金额、有效期、算法、收款人及 trampoline hint。

推进顺序为恢复授权 / 原创建 → 核对所有原操作与可验证的 fulfillment / cancellation → 校验签名请求并保存 / 提交 → 入账 TLC 获得完整本地证明后授权释放并立即 settle_invoice → 再核对双 lane 和 RPC 余额。收款不能因发票 Expired 推断已接受 TLC 失败。每次 settle 重试重新执行安全释放校验。

查询不持久化远端响应，不输出远端原始错误、preimage 或凭证；远端不可用仍输出本地记录。resume 只定位目标，签名推进允许同通道其他原授权；watch 持續前台。原实现全命令支持 --account 和 --config；目标选择入口按下文第 6 节调整，timeout 仅停止本次等待，Ctrl-C 同样保存恢复信息。

关闭条款持久化最新无 TLC 的 SDK 双 lane 余额，远端余额加 reserves 必须匹配；退款减关闭费后按原出资脚本核对。

### 2. 清单、绑定与升级

版本 2 建议包含：

```text
Registry {
  version: 2,
  legacy_current: Option<AccountId>,
  users: [UserEntry; 4],
  accounts: Vec<AccountEntry>
}
UserEntry {
  number: 1..=4,
  funding: { offckb_index, lock_script, address },
  current_account: Option<AccountId>,
  last_closed_account: Option<AccountId>,
  initialized: bool
}
AccountEntry { id, user: Option<UserNumber>, archived }
```

- `initialized` 区分首次身份尚未创建完成与关闭后的空闲，避免重跑初始化误创建下一轮。首次写入绑定和预留账户 ID 后，完整创建身份才能标为已初始化。
- 历史列表由不可变的 `AccountEntry.user` 关联；租户归属通过该账户及 `account.json` 中的 tenant_id 确定。新建账户先保存用户归属，注册与恢复校验身份和 tenant_id 一致；归档和下一轮分配均不得修改旧记录的 user，不用可变目录或单独重置 signer 文件表示轮次。
- 校验四个编号和索引完整、唯一、准确；current 和 last_closed 必须指向存在且归属匹配的账户，last_closed 必须已归档且本地关闭完成。清单损坏拒绝覆盖。
- 读取时先分辨版本，再按对应结构严格反序列化；不能直接用 v2 结构解析带 `deny_unknown_fields` 的 v1 文件。
- 查询 v1 只展示历史及未初始化提示，不触发迁移。`admin init-accounts` 承担 v1 → v2 写入，保留原 ID、归档标记、目录、密钥、token、`channel.json` 和 `payments.json`；原 `current` 留在 `legacy_current` 仅供展示，不作为新默认入口。
- 旧账户的 `user` 为 `None`，不自动绑定用户 1，不根据原钱包编号推断用户归属；已有历史通道金额与退款脚本完全不改。
- `init-accounts` 先验证现有清单、已初始化的 LSP 配置及 offckb #6～#9 公开数据，排除明确冲突后再写用户清单与本地身份；不修改 LSP YAML 或 Biscuit 密钥。复用现有本地原子保存，不声称多个账户文件更新为一个事务。
- 中途失败保留绑定、预留 ID 和完成的身份，不回滚前一步 init-lsp 已完成的配置。重试 init-accounts 只补尚未开始的身份或已完整写入身份的标记；若已有 SDK 数据缺文件，沿用现有拒绝覆盖策略，报告具体恢复障碍，不另生成密钥掩盖错误。

### 3. 选择及锁顺序

- 编号解析后获得用户锁，再在短期清单锁下解析或预留当前账户，获得账户锁后释放清单锁，随后才进行 RPC。用户锁覆盖命令直至最终归档完成。
- 锁使用非阻塞模式。为避免账户锁与清单锁反向竞争，关闭引擎完成后先释放账户锁，保持用户锁，再按“清单锁 → 账户锁”重新读取关闭记录、核对原账户指针并归档。
- 历史命令沿用“清单锁 → 账户锁”，不修改用户指针；同一身份仍由账户锁互斥。`accounts` 仅读取原子文件快照，不获取用于写入的账户目录锁。
- 新开通锁在用户锁之后、进入账户选择及网络推进之前获取；初始化批量用户锁按编号升序获取，再操作清单。所有锁均不阻塞等待，竞争时返回可理解的提示。
- 所有函数传递已解析的用户绑定及 `AccountId`，避免下层再次按全局默认值选择。输出包含用户编号、账户 ID、钱包编号，恢复命令带回 `-u N` 或原 `--account ID` 及 `--config`。

### 4. create-channel

1. 解析参数，加载配置，检查用户初始化及公开钱包绑定；无当前账户时预留新账户 ID 并持久化归属，再创建身份。已有当前账户只恢复，不替换。
2. 在同一账户锁下执行注册/恢复。已注册账户不重复注册，也不要求重新读取管理 token；尚未注册时使用现有 operator token。
3. 沿用注册响应丢失保护：先核对服务端租户；已存在但本地缺 access token 时报告“注册结果待核对/凭证无法找回”，不再注册另一身份。
4. 复用开通引擎。新意图取显式金额或 1000 CKB，`Wallet::load(config, binding)` 获取该用户的钱包及 LSP #5，核对余额、阈值和网络，保存完整 `Terms` 后提交。
5. 已有意图使用保存的金额、钱包和请求，核对归属及运行时脚本，不应用新默认金额或重新加载为其他钱包。`Ready` 核验原完成结果后返回；关闭阶段要求先恢复关闭。
6. 注册及开通整个网络流程共用默认 120 秒等待预算；超时保留进度并输出同用户恢复命令。业务结果及状态提示沿用现有 ChannelReady 和链上确认标准。

### 5. close-channel 与归档

继续使用现有关闭引擎的请求、签名、等待链上确认及双方退款核验流程，不将“已提交关闭请求”或“远端报告关闭”作为成功。仅将返回值区分为 `NoChannel` 或包含账户 ID、channel ID、关闭 hash 的 `ClosedVerified`，便于原流程成功后追加归档；错误继续返回 `Err`，超时保留进度。当前已有本地 `Closed` 记录时，仍按原条款核验链上关闭与退款后返回 `ClosedVerified`。

仅收到 `ClosedVerified` 才进入归档阶段：

1. 保持用户锁，按前述顺序重新锁清单及原账户，核对返回的 ID、关闭证据和用户当前指针。
2. 在同一份清单原子写入中将账户标为 archived、清空 `current_account`、设置 `last_closed_account`；保留账户的 user 和 tenant_id 永久归属，不删除或移动账户目录。
3. 清单保存失败保留原指针；原 `channel.json` 已关闭状态不回滚。重试先复核原结果，再重复该元数据更新。
4. 清单已归档但输出前中断时，空闲用户通过 `last_closed_account` 找回原结果；初始从未开通的空闲情况返回 `NoChannel`。
5. 历史 `--account` 关闭只归档该记录；若记录已属于某用户且仍是其当前轮次，拒绝历史关闭入口，要求通过 `-u N` 执行完整流程，避免绕过用户锁或破坏指针。

关闭不自动推进未授权付款、不强制关闭、不按原始出资额代替最新结算余额。不存在通道、TLC 未结算、余额/归属不一致、链上确认缺失和退款验证失败均不触发归档。

### 6. 收付款和查询接入

- `ClientOptions` 改为明确选择器，各命令复用该解析与定位。`pay`、`create-invoice`、`watch` 仅允许用户当前账户；其余支持前述历史入口。
- payments 文件位置、版本和账户级归属不变；用户 N 查询 hash 时，只查所选账户，找不到时报错，不跨用户或跨轮次自动搜索。
- 历史 --account 查询/恢复保留并展示该身份的原用户归属，使用该账户原租户凭证；不把历史租户重新关联至当前轮次或另一用户。旧 v1 未绑定账户保持单独的历史入口。
- 恢复提示改用新命令名及用户参数。保留原付款 hash、费用、秘密及签名恢复规则，避免合并流程改变已有授权。
- `status` 和 `accounts` 不因用户无通道而注册或分配下一轮；清单未变时不调用保存。
