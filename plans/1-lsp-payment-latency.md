## 规划方式

## 背景和总体目标

当前普通 Fiber 支付被观察到可以在几十毫秒内完成，LSP 支付则达到几百毫秒甚至秒级。普通 Fiber 的原始计时样本、跳数和完成条件尚未提供，暂不能直接计算两者差距。

2026-10-14 的现有 LSP 支付证据：

| 样本 | 已有结果 | 解释边界 |
| --- | --- | --- |
| 历史付款 `0x56d6d6b6…` | 服务端从付款启动到付款端 Success 约 8679.7ms | 旧 CLI 存在每轮 500ms 等待，ACK 间隔与该等待相符；单次历史样本 |
| 新版付款 `0x491d4b05…` | 服务端约 882.2ms，付款 CLI 约 970ms，收款 CLI 约 691ms | 已使用事件等待；包含两条私有通道、外部签名、收款原像释放和结算 |

服务端时间由已有 [.state/devnet/lsp.log](../.state/devnet/lsp.log) 提取；CLI 时间来自 [README 收付款记录](../README.md#7-收付款及离线恢复)。这些数据提供排查起点，不作为统计基准。

本项目的 LSP 将租户 Fiber runtime 与 Public T 放在同一进程通信，仍执行 Fiber commitment 和 revoke/ACK 状态机；客户端持有签名权。因此减少内部传输耗时，并不自动抵消客户端 RPC 和持久化的新增成本。

总体目标：减少当前在线支付中每次签名的额外工作，建立与普通 Fiber 可比较的统计结果，同时保持既有资金校验、签名授权、故障恢复和完成定义。

## 产品需求与范围

1. 优先优化同一 LSP 下两个已在线账户之间的 CKB 支付；保留账户到普通 Fiber 节点的收付款兼容性。
2. 保持 `pay`、`create-invoice --wait`、`watch`、`resume` 的前台使用方式，超时或退出仍能按原 hash 恢复。
3. 付款完成仍要求远端 Success、SDK 双 commitment lane 的 TLC 移除及余额核对；收款完成仍要求 Paid 和对应的 SDK/余额证据。
4. 已完成历史付款不再参与新支付的常规查询、重复授权和进度持久化。历史查询及恢复资料继续保留。
5. 提供可选、脱敏的耗时与调用次数统计，以区分 CLI 启动、远端支付、收款余额更新、签名和落盘耗时。
6. 本阶段不调整 Fiber 协议及密码学算法，不增加托管签名、后台守护进程或自动付款重试，不扩大链上操作能力。

## 约束与依赖

- 不自动清理现有 devnet、通道、账户、付款、原像或签名历史。性能实验与故障注入使用隔离数据。
- 保持 offckb 管理 CKB/普通节点、Shell 单独启动 LSP 的分工；测试逻辑使用 Rust，不扩展复杂 Shell。
- 同级 `../fiber` 的 SDK 改动属于独立仓库范围，需要明确授权；只改 CLI 的阶段可单独交付测量结果。
- 保留 nonce 防重用、commitment 校验、原像 hash 校验、live funding 核验、恢复窗口检查及必要的同步持久化。
- 不以关闭 fsync、降低完成条件、提前释放原像或把结果未知解释为未发送来达到目标。
- 计时选项或可观察行为变化同步更新 README 和收付款文档。
- 编译标识、Release 模式、存储、节点配置、通道跳数和完成条件必须纳入基准记录。

## 产品验收条件

以下性能阈值为建议值，待开发者确认；本轮没有开展新测量。

| 条件 | 验收方式 |
| --- | --- |
| 可比较的基准 | 同机、相同金额/跳数/结算终点，记录普通 Fiber 与 LSP 的冷启动及在线稳态结果；报告 p50、p95、失败率和样本数 |
| 在线支付延迟 | 在线稳态付款端 Success 暂定 p50 ≤ 200ms、p95 ≤ 400ms；同时报告相对基线降幅及 CLI 完整完成耗时，不把单笔 882ms 视为 p50 |
| 历史数量不放大推进成本 | 完成历史从 0 增至 1000 条、活跃付款保持 1 条时，新付款热路径的远端查询与耐久写入次数不随历史数量增加；启动和完整历史读取耗时单独报告 |
| 完整完成定义 | 成功、失败及到期按原语义核对；不得以 RPC 已接受、余额首次改变或仅一侧 TLC 移除替代最终完成 |
| 恢复能力 | 关键持久化边界中断后能恢复原 hash、原签名请求及原授权；不得重复 send_payment、冲突签名或误释放原像 |
| 兼容性 | 既有文件格式和账户锁继续可用；账户之间及账户与普通节点的双向支付通过验证 |
| 可解释的结果 | RPC、SDK 校验/签名、文件及目录 fsync、链上查询都有次数和耗时证据，不能仅报告总耗时 |

若完成已授权优化后仍未达到确认的阈值，本方案保持未完成，依据测量提交后续设计或验收调整建议，不自行降低目标。

## 执行记录与恢复点

已完成：用户授权的流程简化、CLI、SDK 与签名 RPC 优化已实现；现有数据保留；使用说明同步。
剩余工作：统一自动传票统计、剩余等待归因、完整恢复矩阵及产品验收。
验证结果：单笔 Release 付款端约 1.388s → 1.204s；调用及写入次数显著下降，存储同步变慢抵消部分收益。定向 SDK、CLI、权限、隔离端到端与同请求重放验证通过，详见 1.1。
未验证项：建议 p50≤200ms/p95≤400ms 目标、普通 Fiber 对照、公网和完整故障场景；当前样本未达到数百毫秒目标。

恢复点：结合用户新样本按 1.1.3 继续统一测量，勿将收款等待人工付款的时间算作支付处理耗时。
