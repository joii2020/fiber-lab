## 背景和总体目标

规划起点的 `lsp-cli` 已支持账户、开通、查询、协作关闭和归档；收付款及恢复命令已实现并通过本地验证，真实 devnet 验收尚未完成。账户仍采用一个默认账户加历史账户的模式，新通道固定从 #6 出资。已有流程说明见 [通道与收付款流程](../docs/payment-flow.md)。

本方案同时将 CLI 改为四个固定用户：编号 1～4 分别使用 offckb #6～#9，以 --user/-u 显式选择；合并注册和开通、确认关闭和归档，保留每个用户所有历轮租户及收付款历史。

让客户端通过现有私有通道向普通 Fiber 节点付款、接收普通节点付款，并在退出 CLI、断网或重启后恢复原操作。离线能力必须有明确的状态展示和可复现的联调路径，不能仅将持续运行 `watch` 作为收款方式。

本版将用户“提现出离线”理解为“体现出离线能力”。通道资金提现沿用既有协作关闭流程；新增提现功能不纳入本版，若用户原意为新增提现，需要调整需求范围。

### 多用户模式的合理性

整体合理，现有按账户保存的 SDK、通道及收付款记录可以复用。但必须明确以下语义，否则直接合并命令会产生问题：

1. **用户、钱包和租户归属持久绑定。** 用户编号及 offckb #6～#9 钱包永久对应；用户创建的每个租户永久归属该用户，关闭和归档都不解除或转移这层绑定。当前服务端一个租户只有一个 `private_channel_id`，SDK 也不允许改绑通道；关闭后不能重用该身份开新通道。因此下一轮由同一用户创建新身份和新租户，旧租户仍保留在该用户历史中，模拟真实用户的持久归属。
2. **分别初始化 LSP 和用户。** `admin init-lsp` 只负责现有 LSP 配置和密钥；新增离线 `admin init-accounts` 创建四个本地用户、各自的首轮 SDK 身份及钱包绑定。`create.sh` 在 `init-lsp` 后调用它，再生成管理 token、启动 LSP；`create-channel` 完成服务端注册。
3. **遵从现有关闭完成逻辑后归档。** 现有 `close-channel` 已等待关闭交易链上确认并核对双方退款，合并后的命令继续使用这一完成判定，在原关闭引擎确认成功后追加归档。超时或失败保留当前指针及原租户归属。
4. **钱包绑定贯穿完整交易。** 不仅改变出资账户展示，还必须用于 input 校验、签名、找零及退款；恢复始终使用通道原条款。

本模式是同一操作者在本地管理四个用户身份；不提供操作系统用户隔离或多人权限管理。四用户共享 LSP，LSP / Public T 的出资钱包仍为 #5。

## 产品需求与范围

### 1. 首期范围

- devnet、CKB、固定金额、单笔单路径付款；每个用户使用当前轮次账户及其单条已绑定私有通道，复用现有收付款引擎。
- 支持客户端付款、在线收款、客户端停止签名后的重连收款、私有通道离线缓冲后的恢复，以及各流程中断后的结果核对。
- 日常操作显式使用 `--user/-u`；`--account ID` 保留为指定命令的历史查询与恢复入口，选择规则见第 7 节。`--config PATH` 保留；记录按账户隔离，历史选择不切换用户当前轮次。
- 提供按付款 hash 查询及本地记录列表；查询与推进操作分开，单纯查询不签名、不释放收款秘密、不重新付款。
- 首期不包含 UDT、MPP、无金额发票、keysend、自动再平衡、移动端通知、新的常驻后台服务、强制关闭或链上 TLC 追偿。
- 原收付款实现及其授权保留；多用户改造已实施，命令及真实验证见 2.1.1；完整收付款验收尚未通过。

### 2. 离线语义与能力边界

| 场景 | 应有行为 | 向用户展示的含义 |
| --- | --- | --- |
| 创建发票后退出 CLI，或客户端断网 | 客户端停止签名和释放 preimage；LSP 托管租户可能继续运行，付款可能已向私有通道投递并等待签名 | 待签名 / 待结算，不能承诺一定处于缓冲队列 |
| LSP 与托管租户私有通道离线，付款到达 Public T | LSP 在有效窗口内缓冲上游 TLC，等待私有通道恢复 | LSP 暂存中，尚未到账 |
| 客户端及必要通道在窗口内恢复 | 恢复原账户和原授权，核对实际状态，完成需要的签名及结算 | 展示恢复过程，最终核对入账结果 |
| 超出可安全恢复的时间窗口 | 不释放 preimage，不将过期付款报告为成功；等待并核对服务端的失败及 TLC 清理结果 | 已超时待核对 / 已失败，余额是否释放须单独核对 |
| 付款途中退出或请求结果丢失 | 重连后按原 payment hash 核对与推进，不自动启动新一笔付款 | 结果未知 / 处理中，保留原操作标识 |

离线收款的承诺是“在有效窗口内重连完成收款”。本版不提供客户端长期离线期间自动最终到账，也不支持完全离线发起新的网络付款。

离线窗口不是发票有效期的同义词。当前服务端未投递付款的缓冲截止受以下条件共同约束：LSP 实际缓冲策略、发票到期时间、上游 TLC 可用时间减下游期限预算及安全余量；取最早截止。开始下游投递后，应按该付款的 TLC 与签名恢复条件判断，不能继续单靠缓冲截止判断可恢复性。

### 3. 付款

草案交互：

```text
./lsp-cli pay '<invoice>' --max-fee CKB --timeout SECONDS -u N
./lsp-cli resume --payment-hash 0x... -u N
./lsp-cli payment-status --payment-hash 0x... -u N
```

- 检查发票网络、签名、金额、资产、有效期和当前账户通道是否适用；金额及费用使用 CKB 十进制格式，与现有金额输入习惯一致。
- 必须有明确的费用上限。初版建议首次付款显式传入 `--max-fee`；恢复时使用原授权，不改变金额或费用上限。
- 开始付款前保存原发票、付款 hash、账户及通道归属、金额、费用上限和有效期等授权信息。
- `pay` 推进这笔已授权付款需要的签名并等待结果；同一通道上其他已有授权的操作若影响推进，也只能按原授权处理。
- 相同 hash 的重复执行优先核对和恢复原付款；成功后返回原结果，未明时不盲目再次调用发送。失败后的新尝试策略留待技术阶段确定，首期不自动重试发送。
- 本地 `--timeout` 只表示本次等待结束，不表示网络付款失败或取消；输出 hash 和恢复命令。
- 服务端报告 `Success` 后，还需核对 SDK 接受的结算状态与本地余额；状态未同步时展示“远端成功，待本地核对”，最终核对完成后才展示“付款完成”。

### 4. 创建发票及收款

草案交互：

```text
./lsp-cli create-invoice --amount 1 --expiry SECONDS -u N
./lsp-cli create-invoice --amount 1 --expiry SECONDS --wait -u N
./lsp-cli create-invoice --amount 1 --expiry SECONDS --wait --timeout SECONDS -u N
./lsp-cli watch -u N
./lsp-cli resume --payment-hash 0x... -u N
./lsp-cli invoice-status --payment-hash 0x... -u N
./lsp-cli list-payments -u N
```

- 首次创建发票显式输入金额，建议演示金额为 1 CKB；发票有效期与 CLI 等待超时分别定义。
- 本地生成并持久化 preimage 和 SDK 收款授权；LSP 创建只含 payment hash 的 hold invoice。发票核对并保存成功后立即输出并刷新可分享的地址及 hash，随后按是否提供 `--wait` 决定退出或在线等待。
- 默认不带 `--wait`：输出发票后退出，不启动后台签名进程。没有其他本账户推进进程运行时，用于模拟客户端离线收款；退出本身不保证 LSP 内的租户或私有通道离线。
- 带 `--wait`：输出发票后保持前台在线，复用 `watch` 的签名和结算推进逻辑，直到本张发票收款完成、确定无法继续收款或用户中断；默认持续等待，可用 `--timeout SECONDS` 限制本次等待。无需再启动另一个 `watch` 进程。
- `--timeout` 在 `create-invoice` 中仅与 `--wait` 一起使用；等待超时或用户中断只停止本次在线推进，不取消发票、不等于付款失败，保留原 hash 和恢复资料并输出恢复命令。发票过期时仍须核对已接受付款的实际 TLC 状态，不能仅凭发票过期将处理中付款判为失败。
- 网络响应丢失时保留同一 hash 和创建意图，恢复原创建，不重新生成秘密；最终重放方式在技术阶段核实。
- `watch` 是前台推进命令，持续核对本账户已授权收付款、处理 SDK 验证通过的签名和收款结算；停止后不自动启动后台进程。
- `resume` 有界推进指定操作并等待结果。付款 hash 用于定位操作，但通道签名可能同时涉及其他已授权操作，因此不能承诺完全隔离单笔通道状态更新。
- 默认离线演示顺序为：创建并输出发票 → CLI 退出 → 对端发起付款 → 客户端在有效窗口内通过 `watch` 或 `resume --payment-hash` 上线 → 完成签名、释放 preimage 并核验结算。对端在离线期间可能处理中，超出窗口也可能失败；不能等待付款成功后才上线，也不能将支付请求被接受当作支付成功。
- `Received` 仅表示收款流程尚待结算；LSP delivery 为 `Succeeded`、invoice 为 `Paid` 和客户端余额核验是不同层面的证据，展示时保留区别。
- 仅当 SDK 确认入账 TLC 有完整可恢复证明、链上出资仍有效且剩余恢复时间充分时，才能释放 preimage；最终入账 TLC 移除及余额增加也需核验。

### 5. 查询与用户可见状态

- `payment-status`、`invoice-status` 展示本地记录与远端结果、查询时间、原始状态以及下一步操作；无法访问远端时保留本地记录并明确“远端未核对”。
- 本地收付款列表至少包含方向、hash、CKB 金额、通道、阶段、更新时间和恢复提示；不输出 preimage、私钥或凭证。
- 发票查询展示发票到期时间；能取得 LSP delivery 时另外展示暂存状态、实际缓冲截止和失败原因。拿不到 delivery 不能推断“没有付款到达”。
- 查询不主动唤醒离线租户的目标需要在技术阶段核对：当前用户 RPC 通过托管租户上下文访问数据，不能只因方法名为 `get_*` 就承诺不影响运行状态。
- 管理侧 delivery 查询作为离线联调的证据；普通用户命令不读取管理 token 代替租户权限。首期不新增此接口；普通用户展示现有发票 / 付款查询及本地证据，明确不能推断 delivery 或保证无唤醒副作用。

### 6. 资金及已有操作协作

- 付款需要客户端一侧可用余额；收款需要 LSP 一侧可用余额，均扣除保留金额及必要费用。默认 LSP 注入 99 CKB 时初始收款流动性为 0，需显式准备。
- 推荐联调顺序：客户端先付出 1 CKB，使 LSP 一侧形成余额，再让普通节点向客户端付回 1 CKB；跨普通节点与 LSP 的通道也须具备相应方向流动性。
- `status` 展示双方余额和未结算 TLC，作为收付款结果的交叉检查。
- 有未结算 TLC 或本地结算未同步时，协作关闭继续拒绝；不能通过关闭、归档或清空数据规避恢复。
- 同一账户一次只允许一个推进进程持有现有账户锁。首期 `watch` 或 `create-invoice --wait` 运行时其他账户命令可能因锁冲突被拒绝，停止当前推进进程后查询或创建下一张发票；是否改善并发交互另行确认。
- 账户归档继续保留所有收付款记录、密钥及恢复资料，以及账户/租户的永久用户归属；历史账户可显式选择并恢复原操作。

### 7. 固定多用户及通道生命周期

#### 1. 初始化与固定用户

| 用户编号 | offckb 出资账户 |
| --- | --- |
| 1 | #6 |
| 2 | #7 |
| 3 | #8 |
| 4 | #9 |

- `admin init-lsp` 保留现有 Node3 配置和 Biscuit 密钥初始化职责，不创建用户。
- 新增 `admin init-accounts`，读取已初始化的 LSP 配置，离线创建上述用户、绑定和首轮本地身份；支持 `--config PATH`，默认使用 Node3 配置，不要求 LSP 或管理 token 可用。
- `create.sh` 的初始化顺序为 `admin init-lsp → admin init-accounts → admin create-token → start.sh`；账户初始化失败时按现有脚本逻辑停止，不继续启动环境。
- 初始状态为“已初始化，未注册”；四份身份不同，SDK 根密钥独立于 offckb 出资私钥。
- 用户与钱包的绑定创建后不可更换；每个本地账户及其注册产生的租户永久关联创建它的用户，包括已关闭和已归档的历史记录，不允许转给其他用户或变成未绑定记录。
- 重复初始化复用已有身份和绑定，不重置当前轮次、归档历史或轮换密钥；已关闭用户保持空闲，不因重跑初始化创建下一轮身份。
- 用户及历史记录保存在项目 `.state/fiber-lsp-client/`，不增加 Shell 账户逻辑。
- 首期固定四个用户，不提供增删用户、修改钱包、默认用户或批量开关通道。

#### 2. 命令与用户选择

| 命令 | 用户参数 | 行为 |
| --- | --- | --- |
| `admin init-lsp` / `admin create-token` | 无 | 管理整套 LSP 环境，保持离线语义 |
| `admin init-accounts` | 无 | 离线初始化四个固定用户、钱包绑定及首轮本地身份，已有记录复用 |
| `accounts` | 无 | 列出四个固定用户及本地状态 |
| `accounts --history` | 无 | 同时列出历轮账户和迁移前的旧账户 |
| `create-channel -u N` | 必填，1～4 | 创建或恢复该用户本轮身份，注册租户并开通或恢复通道 |
| `close-channel -u N` | 必填，1～4 | 协作关闭、核验退款，再归档本轮身份 |
| `status -u N` | 必填，1～4 | 查询该用户身份与通道；空闲时展示最近一轮摘要 |
| `pay` / `create-invoice` / `watch` | 必填，1～4 | 只处理该用户当前账户及其已有授权 |
| `resume` / `payment-status` / `invoice-status` / `list-payments` | 必填，1～4 | 只定位该用户的操作，不跨用户寻找 hash |

- 日常用户命令没有隐式默认值；缺少、越界或冲突参数在任何注册、签名、转账前拒绝。
- `create-channel --funding-amount` 单位仍为 CKB、最多八位小数。仅新开通意图默认 1000 CKB；恢复省略参数沿用原金额，显式传入时必须一致。实现中保留 `Option`，不能让解析器默认值覆盖恢复金额。
- 保留 `--config PATH`、通道操作 `--timeout`（默认 120 秒）、关闭 `--channel-id`，以及收付款现有金额、费用、hash、等待等参数。
- 建议移除独立的 `create-user`、`open-channel`、`archive-account` 和 `list-accounts`；用新命令及文档覆盖原使用方式，不保留隐式默认账户入口。
- 为旧数据及历史恢复保留 `status`、`close-channel`、`resume`、`payment-status`、`invoice-status`、`list-payments` 的 `--account ID` 模式：与 `--user` 互斥，二者必选其一。历史模式只操作指定账户，不切换用户当前轮次、不创建新身份或新付款；历史关闭仍须核验成功后归档该记录。
- 未选用户且未选历史账户时不回退到迁移前的默认账户。

#### 3. 列表与状态

`accounts` 默认仅读取本地清单与摘要，无需节点、管理 token、配置文件或 offckb 命令可用；不注册、不签名、不推进交易、不写回查询结果。

建议列：用户编号、offckb 编号、当前账户 ID、tenant_id、本地阶段、历史账户数。`--history` 额外显示历轮账户 ID、所属用户或“旧账户未绑定”、归档标记和本地通道阶段。

本地阶段包括：已初始化未注册、注册待核对、已注册未开通、开通中、可用（本地记录）、关闭中、空闲（最近一轮已关闭）、记录异常。远端或链上无法核验时不能把本地 `Ready` 当作实时可用；`status -u N` 沿用现有远端及链上核验，并区分本地记录与核验结果。

尚未初始化用户时明确提示执行 `admin init-accounts`，不能把推导出的 1～4 行当作已经创建的用户；LSP 配置尚未初始化时先执行 `admin init-lsp`。清单损坏时报错；单个账户文件异常时展示该行异常，其余行仍可查看，不自动补造身份。

#### 4. 生命周期与重复执行

```text
init-lsp：LSP 配置及 Biscuit 密钥
init-accounts：用户 N + 固定钱包 + 首轮本地身份（未注册）
create-channel -u N：该用户的本地身份 → 注册该用户的租户 → 开通中 → Ready
close-channel -u N：Ready → 原关闭逻辑的链上及退款确认 → 归档本轮 → 用户空闲
下一次 create-channel -u N：同一用户、同一钱包 + 新身份 → 该用户的新租户 → 新通道
所有历轮身份及租户：始终属于用户 N
```

- 注册、开通或关闭中断时，重试选择原身份和原操作；不因超时创建下一轮。
- 当前通道已可用时重复 `create-channel` 核对并返回原通道；原金额不一致时报错。
- 当前处于关闭中时拒绝创建通道，提示先恢复关闭；处于“本地已关闭、归档未完成”时也先完成原关闭命令。
- 无通道且无开通意图时 `close-channel` 说明没有可关闭通道，不归档已初始化或已注册身份。开通未完成时引导恢复 `create-channel`，不将一般成功返回值当作关闭完成。
- 刚归档后重复关闭，通过最近关闭账户核对并返回原结果，不再归档其他身份；已有下一轮当前账户时以当前账户为准。保留 `--channel-id` 可明确限定要关闭的通道。
- 空闲用户的 `status` 可以读取最近关闭摘要；收付款相关命令不隐式回退到上一轮，提示通过 `accounts --history` 和 `--account ID` 选择历史。
- 归档仅更新归档标记及当前/最近关闭指针，不修改账户或租户的用户归属，不删除文件、不注销服务端租户、不撤销未过期发票。历史发票仍归属该用户的原租户，不能迁移至新轮次或其他用户。

### 必须遵守的边界

- offckb 管理 devnet 与普通节点；Shell 单独启动 LSP。收付款状态机和恢复逻辑用 Rust 实现，Shell 仅组合明确命令。
- 不自动清理已有运行数据，不重配用户钱包、不更换进行中的账户身份。仅用户显式执行 create-channel 且上一轮已确认关闭并归档时，按固定用户归属创建下一轮身份、租户和通道；普通收付款和查询不自动开通道。
- 实施后同步更新 README 和 `docs/payment-flow.md`，明确可执行命令、离线限制、流动性准备和恢复方式。使用说明随实际交付更新，未验证内容单独注明。
- LSP 必须持续运行才能暂存离线付款；LSP 重启后的缓冲恢复另有验收，不能等同于客户端离线。
- 用户普通收付款只使用用户凭证；管理侧用于显式构造私有通道离线场景和观察证据。
- 若真实 CLI 退出后不能自动令私有通道离线，首期保留两种离线场景，真实 `Deferred` 通过显式管理操作构造。是否增加用户 `offline` 命令、存在性检测或服务端接口，需先确认产品要求，不能当作现有能力。

- 新租户会累积在服务端，归档不释放租户名额；注册触及配置的租户上限时明确报错，不自动清理或更改服务端上限。
- 多用户钱包互不相同，但共同使用 LSP #5 的资金 cells。首期链上开通串行执行，避免同一 LSP live cell 被并发选中；不同用户收付款及前台推进可并行，同用户命令继续互斥。

## 产品验收条件

| 场景 | 可观察的通过条件 |
| --- | --- |
| 在线付款 | 普通节点创建 1 CKB 发票；CLI 付款，付款状态成功且本地结算余额及 TLC 与授权相符，手续费不超上限 |
| 在线收款 | `create-invoice --wait` 立即输出 hold invoice 后保持在线；普通节点付款，无需另启 `watch` 即可完成收款，发票 `Paid` 且 SDK 核验入账和余额增加后命令退出 |
| 客户端停止签名后收款 | 不带 `--wait` 创建发票，命令输出后退出且所有本账户推进进程均停止；对端发起付款，确认未最终到账且不释放 preimage；窗口内通过 `watch` 或指定 hash 的 `resume` 上线，原 hash 收款完成 |
| 在线等待中断恢复 | `create-invoice --wait --timeout` 超时或用户中断后保留发票、原 hash 和授权，不误报付款失败或取消发票；在仍可恢复的窗口内重新上线，原发票完成收款且只入账一次 |
| 私有通道真实离线缓冲 | 显式管理操作使私有通道离线并核对证据；对端付款，管理查询出现 `Deferred` 和截止时间；恢复租户/通道及客户端后原 hash 完成投递与入账，无重复余额变化 |
| 离线超过窗口 | 选择可控的短窗口并保持私有通道离线，最终失败且上游 TLC 已失败移除；付款方余额按实际费用恢复，客户端不出现入账、不释放 preimage；区分等待超时与实际失败 |
| 付款中断恢复 | 在发送响应丢失和签名提交响应丢失处中断，重启按原 hash 核对并推进，最终只支付一次且原授权不变 |
| 收款结算中断恢复 | 在创建发票响应丢失、提交签名、释放 preimage 前后中断，恢复后核对原记录，最终只入账一次；无法恢复时明确原因并保留资料 |
| LSP 重启 | 存在缓冲或处理中付款时重启 LSP；原记录可查，仍有效则恢复，失效则明确失败，不重复派发或误报成功 |
| 查询和权限 | 本地与远端状态来源可区分；查询不签名、不释放 preimage、不发送付款；普通用户不能访问其他租户或借用管理凭证 |
| 关闭与归档协作 | 未结算 TLC 阻止关闭；收付款结算同步完成后可按现有规则协作关闭，退款反映最终余额；归档不丢失收付款恢复资料 |
| 用户初始化及脚本顺序 | `admin init-lsp` 仅配置 LSP；停止 LSP、尚无管理 token 时执行 `admin init-accounts`，得到四份独立本地身份及准确的 #6～#9 绑定；重复执行不改变身份、绑定及历史。`create.sh` 在 `init-lsp` 后、签发 token 和启动前调用 `init-accounts`。 |
| 离线用户和历史列表 | `accounts` 离线列出四用户及各自阶段；`--history` 可找到旧默认账户及所有历轮记录，查询不改写账户内容。 |
| 四用户开通及钱包核验 | 用户 1～4 分别通过一次 `create-channel -u N` 完成注册、出资和 ChannelReady 核验；核对各自 #6～#9 的出资、找零和扣费，LSP 使用 #5。 |
| 用户选择与操作隔离 | 所有日常用户命令必须明确选择用户；一个用户的付款 hash、签名记录和文件不能被另一个用户读取为自己的操作或推进。 |
| 租户永久归属及下一轮 | `close-channel -u N` 沿用现有等待链上确认及核对双方最新余额退款的完成逻辑，成功后归档；用户编号、钱包保持不变，再次开通使用不同 tenant_id 和新目录。新旧账户及租户始终归属创建它们的用户，旧历史仍可按该用户找到，不能转移或解除归属。 |
| 开关及归档中断恢复 | 开通、关闭超时及归档落盘中断后可恢复；不重复出资、不重置身份、不提前释放当前指针。注册结果丢失且凭证无法找回时保留异常并拒绝盲目重注册。 |
| 用户与开通竞争 | 多用户并行操作不串用钱包或身份；同用户竞争明确拒绝，链上开通竞争明确拒绝且可在前一次结束后重试。 |
| 旧数据与文档升级 | 升级后原账户目录及密钥保持原路径和内容，旧通道可按 ID 恢复与关闭；README 示例和帮助均采用新接口，并说明初始化、恢复及历史边界。 |

真实离线、过期及 LSP 重启验收需要实际 devnet 和节点证据，不能只依赖模拟 RPC。未能完成的场景须单独记录，不能计为通过。
