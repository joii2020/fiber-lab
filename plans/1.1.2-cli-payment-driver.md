## 详细技术设计

### 活跃集合与历史保留

从 Book 构建内存中的活跃 hash/index 集合：IntentSaved、Submitted、Pending、RemoteSuccess、ExpiredPending，以及所有仍有发送/签名/结算歧义的操作。

Complete、已核对 TLC 清理的 Failed 和已核对无入账 TLC 的 Expired 不参与常规推进；原授权及历史记录继续保留。加载时发现终态与必要本地恢复资料矛盾，报错并保留文件，不把记录静默移出处理。

target 指定最终等待对象和展示范围；同一通道的其他活跃授权仍可被签名步骤依赖，不把 target 过滤错误地用作整个通道的授权集合。启动仅恢复活跃操作的授权，终态历史通过 SDK 已持久化的证据继续校验；原 pending_signature 独立恢复。

### 有界连续推进

单次批次流程：

1. 启动先取得事件游标，再读取远端当前状态；检查通道归属与可支付状态，网络身份核验避免在同一启动流程重复进行。
2. 刷新活跃操作的必要初始证据，恢复已保存的发送/签名请求；沿用 send_once 的结果未知规则。
3. 获取当前待签请求，判断其 TLC 新增、移除及 revocation 依赖。
4. 若移除 TLC 所需 fulfillment/cancellation 证据未在 SDK 中授权，按 hash 查询该操作并核验。满足依赖后调用 SDK 准备/确认。
5. 先同步保存原请求与提交参数，再提交签名；已保存请求只按原 request ID、原内容重放。
6. 成功后立即取下一待签请求；每次已完成本地 commitment 后检查活跃收款是否具备释放条件。实际释放尝试必须重新核验 live funding 和安全窗口。
7. 没有待签请求、观察到无进展的重复 ID 或最多处理 32 个请求时结束批次，刷新活跃操作和通道、核对余额、提交必要变化及输出进度。
8. 未完成时用原游标等待更新。游标落后则立即继续；无变化时挂起，超时用于补查。退出/截止时间在批次内也检查，不能无限 drain。

32 为防止长批次饿死进度与截止检查的初始上限，不是固定等待次数。没有签名时直接进入收款释放/状态核对，不要求等满批次。

同一 request ID 的成功响应不代表可再次产生新签名；重复状态停止当前批次并补查/等待。响应丢失时保留原 pending_signature，恢复仅核验和重放同一个请求，不重新发起付款。

### 签名事件与提交响应

`ChannelSigningUpdate` 包含 channel_id、revision 和既有 ChannelSigningStatus；复用其中的 settlement 和 peer session evidence，由 SDK 独立验证。wait_channel_signing_request 先等既有持久化通知，再读状态，游标先于状态读取，后续变化不会丢失。它不是跨通道/付款的一致快照。

submit_channel_signature_and_get_next 先执行原 submit 的 request ID、重放和签名校验，再读当前游标与可见下一请求；没有下一请求时由客户端继续等待。旧 RPC 不变。租户处理使用同一 namespace 和通道归属检查；等待需要 channels read，组合提交同时需要 channels read/write。

成功的 settle_invoice 响应在本次进程内记为已确认，不因后续签名事件再次释放；新进程没有该确认缓存，release_started 不证明远端接受，恢复重试仍重新做完整链上与窗口核验。

### 必要证据先于签名

付款端 preimage 的获取不能推迟到 TLC 移除签名之后。使用待签 settlement 与 SDK 当前 lane 的 TLC 差异决定哪些活跃 hash 需要补证；新增付款的本地授权和签名内容仍由 SDK 全面核验。

安全校验缺失、hash/金额/费用不一致、SDK 拒签或通道不再可链下推进时停止，保留资料。协议错误不作为跳过检查或切换快速路径的理由。

收款端 release_started 不能作为跳过 live funding 校验的依据，也不能证明 settle_invoice 已到达服务端。已释放但远端仍 Received 时先查询确认，需要重试则执行完整核验并提交同一原像；不重复释放未知秘密。

### 付款记录的变化与提交

区分安全状态、核对结果和展示缓存。`refresh` 返回变化信息，不再每条历史/活跃记录都立即重写全 Book；常规远端状态刷新在批次末合并保存。

仍立即同步保存：首次 send_started；待提交签名；release_started；需要在网络动作前保留的授权/原像证据。完整完成结果在输出完成前保存。SDK 自身每次必要授权仍保持现有耐久提交。

updated_at_ms 只在有实际状态/证据变化时更新，防止无变化也生成 dirty。latest_progress 作为当前进程展示缓存，持久化旧字段继续读取兼容；超时/中断优先输出最后一次内存观察，不以写入心跳维持诊断。

对 account.json 比较会话实际变化；当前收付款请求处理通常没有改变 HostedSessionState 时跳过保存。变化检测不跳过 SDK signer store 的落盘。

Book 初次解析和整体保存仍随历史大小增长。本阶段保证不逐条进行完成历史的 RPC/授权；若全量保存继续主导耗时，记录到后续存储候选，不承诺历史全部为常数开销。

### 状态新鲜度与最终完成

远端通道状态在批次起止读取，批次内 SDK 校验和服务端 submit 的状态机检查仍生效；签署关闭/公告等请求继续拒绝。

最终 reconcile 使用本次批次后新查询的远端状态及最新 SDK 双 lane 记录，保留 pending TLC、双方余额、原 TLC 接受与移除的检查。取不到足够新鲜的证据就继续等待，不能仅因本次请求已提交成功退出。

## 产物与验证

产物：按活跃付款推进的 CLI、有界签名循环、减少重复保存的付款账本及行为说明。

必要验证：

- 1000 条完成历史加 1 条活跃操作：完成历史查询/授权次数为零，活跃操作查询和安全写入次数不随历史数量增加。
- 真实 TLC 移除场景：无 preimage 拒签；正确证据先授权再签名；错误原像或取消冲突仍拒绝。
- 事件在游标取得、查询、提交和批次核对之间发生，能继续取得下一状态；同 ID 重复无忙循环。
- pending_signature 写入前/后、提交响应丢失、send_started 写入后、release_started 写入后中断并恢复原操作。
- 成功的双方支付、watch 多个活跃操作、失败后的 TLC 清理、到期、通道关闭和超时；只有完整条件满足才输出完成。
- 定向测试使用 mock/临时目录，真实付款使用隔离 devnet；用户现有数据不参与故障注入。

不以新增“调用了某函数”测试替代这些时序、恢复和工作量验证。
