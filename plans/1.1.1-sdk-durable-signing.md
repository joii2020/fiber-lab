## 详细技术设计

### 幂等授权不递增 revision

update_commitment 在本地候选状态执行授权/resolve 后，与原 commitment 状态做结构或确定性的编码比较。授权确实没有变化则返回成功，跳过 revision 增长和 CAS；存在变化时沿用原 CAS 重试循环。

对同一个 payment_hash 重复授权相同条款、重复 fulfillment/cancellation 使用相同终态均可短路。冲突条款、错误原像或 fulfillment 与 cancellation 冲突仍报错，不能以幂等优化吞掉校验错误。

单个同值 put/CAS 的后端优化只能在 expected 条件已匹配后短路，不能因为 replacement 相同而忽略 CAS 条件。SDK 内容变化检测是主要入口，FileSignerStore 后端仍遵守 SignerStore 原子条件语义。

### 签名与下一轮 nonce 组合提交

新增 SDK 内部组合路径，返回签名与 next_material；按需要新增公开组合方法，原有 sign_commitment/sign_revocation/sign API 保持兼容。HostedSession::sign_pending 选择组合路径，去掉签名后两次独立 get_musig2_nonce 持久化。

单次新签名的流程：

1. 读取原 signing state，并核对 PreparedSigning revision、nonce slot、内容和本地授权。
2. 按现有规则在确认时重新校验 commitment/revocation、时间和恢复证据。
3. 在候选状态生成签名和必要的完整恢复证据，并记录签名请求历史。
4. 推导 next_material，在同一候选状态记录下一 commitment/revocation nonce slot 的发布状态；已发布的 slot 不重复变化。
5. 一次增加 revision，并以同一个 expected state 执行一次 CAS。
6. CAS 及耐久提交完成后返回签名与 next_material；此时才允许 CLI 保存提交参数并进行网络提交。

签名可在内存生成，但在 CAS 成功前不得向调用方、日志或网络输出。CAS 冲突或存储失败时不返回结果；重新 prepare 后继续，不用旧 prepared state 自动覆盖新状态。

已签请求回放必须重验原内容、nonce 和当前允许的恢复路径。如果既有旧 API 记录了签名但没有发布 next_material，组合路径可补充一次缺失的 nonce 状态提交；这属于旧数据补齐，不要求其满足“新签名仅一次 CAS”的正常路径计数。

### 持久化与失败边界

FileSignerStore 继续在候选快照成功落盘后替换内存状态。文件和目录 fsync 都保留；写入失败进入现有 fail-closed 状态，不让后续 get/sign 继续使用未确认资料。

本阶段不引入后台 flush，也不跨 SDK store 和 payments.json 合并事务。CLI 的原请求、签名和提交参数仍在 submit_channel_signature 前单独耐久保存；跨文件中断通过原 SDK 签名历史及原请求校验恢复。

不单独把 fsync 放进可被取消的 spawn_blocking 调用：调用方取消后写入可能仍完成，若内存发布或错误记录丢失会制造状态歧义。异步存储执行模型属于后续专项，不能作为本阶段的快捷改动。

### 文件和 API 兼容

保存原 StoredSigningState 布局与版本，组合后的记录仍是现有 nonce/签名/恢复字段。既有数据无需迁移；旧签名 API 继续通过原测试。

组合路径实现复用统一的状态校验和候选提交逻辑，防止新旧 API 的 nonce、highest_signed 或 recovery 规则分叉。仅 HostedSession 的内部选择发生变化，不增加 CLI 钱包能力。

重写整个 SDK 快照及累积历史仍存在。本阶段通过减少提交次数获取收益；如果测量显示序列化或快照大小已成为主要开销，将结果交给 [1.1 后续候选](1.1-payment-driver-and-persistence.md#5-测量后的后续候选)，另行设计存储迁移。

## 实施步骤

1. 实现同值授权短路，验证重复授权没有 revision 或 CAS 变化，冲突仍被拒绝。
2. 实现签名与 next_material 的候选状态合并，保留原 API 并共用校验逻辑。
3. HostedSession 切换组合路径，验证新签名的实际 CAS/落盘次数；测试旧数据补齐路径。
4. 对候选生成、CAS 冲突、落盘失败、返回前中断及 CLI 重放资料写入失败做恢复验证。
5. 同时重新编译 SDK/CLI，运行隔离 devnet 双向支付并复测总延迟及签名分项。
6. 回填测量、未达目标项及恢复点，完成后提交 [1.1](1.1-payment-driver-and-persistence.md) 的完整技术交付验收。

## 产物与验证

产物：幂等 SDK 授权、一次 CAS 返回签名和 next_material 的组合路径、兼容 API 和验证记录。

必要验证：

- CountingStore 统计同值授权为零次写入，新签名及下一轮 nonce 为一次 CAS。
- 旧签名 API、旧 signer.bin、已经发布 nonce、已经签名但缺少 next_material、同请求重放的兼容场景。
- 修改签名内容、跨通道请求、nonce 重用、revocation 无可恢复 successor、错误原像和未授权 TLC 移除继续拒绝。
- 同一 signing state 并发 CAS 只允许正确的一方完成；失败方不返回可提交的新签名。
- 临时文件 store 的 fsync/rename 失败及关键中断点：恢复只能读取耐久状态，不能重复付款或产生冲突签名。
- SDK 定向测试按同级 Fiber 的 AGENTS.md 使用 nextest；真实支付和故障注入使用隔离数据，不涉及现有账户。
- 用统一基准报告新签名 CAS 次数、CLI 本地写入次数、签名分项以及最终 Success/完整完成的 p50、p95 和失败率。
