## 当前事实

下表为优化前定位依据；本轮实现与验证结果见执行记录。

| 事实 | 来源与含义 |
| --- | --- |
| 已有事件等待 | [CLI drive / wait_channel_update](../fiber-lsp-client/src/payments.rs)、[服务端等待](../../fiber/crates/fiber-lib/src/rpc/channel.rs)；无变化才最多等待 5 秒，已有能力不重复实现 |
| 内部传输为进程内通信 | [tenant runtime](../../fiber/crates/fiber-lib/src/lsp/runtime.rs)；现有状态机仍要求逐步完成 commitment 和 revoke/ACK |
| CLI 每轮只处理一个请求 | `drive()` 中一次 `sign()` 前后执行状态查询、原像检查、余额核对及保存 |
| 完成历史进入每轮处理 | `drive()` 遍历整个 `Book.operations`，`refresh()` 查询并保存所有记录；target 过滤仅用于部分展示和退出判断 |
| 同步保存成本被反复放大 | [FileSignerStore::change / atomic_write](../fiber-lsp-client/src/store.rs)；单 key 更新先复制整个 SDK store，再同步保存整个快照；每次保存同步文件和目录 |
| 幂等授权仍产生写入 | [SDK update_commitment](../../fiber/crates/fiber-lsp-sdk/src/signer.rs)；重复同一授权或 fulfillment 后仍递增 revision |
| 签名与下一轮 nonce 分别持久化 | [HostedSession::sign_pending](../../fiber/crates/fiber-lsp-sdk/src/session.rs)、`get_musig2_nonce()`；可在不改变协议的前提下合并耐久提交 |
| 原像释放依赖独立链上查询 | [Wallet::live_cell](../fiber-lsp-client/src/wallet.rs)；属于现有安全边界，不能删掉或由 LSP 的提示替代 |

尚未确认 fsync、RPC、SDK 密码学校验及 actor 排队的具体占比。首次优化优先移除已确认的重复工作，而不预设某一耗时一定占主导。

## 技术要点

### 1. 统一计时与对照

基准分为 CLI 启动/恢复、服务端付款生命周期、收款余额更新、双方完整完成，以及外部签名各分项。使用单调时钟计算区间，不用不同进程的墙钟相减作为精确耗时。

普通 Fiber 与 LSP 使用相同跳数和最终 Success 终点；普通自动发票与 LSP hold invoice 的差异单独说明，并增加普通节点 hold invoice 对照以隔离收款端释放策略。CLI 启动成本与协议稳态分别报告。

测量仅记录支付标识、请求标识、方法、阶段、耗时和次数；不记录 token、私钥、原像、RPC 完整请求/响应或签名资料。

详细设计见 [1.1.3](1.1.3-payment-latency-baseline.md)。

### 2. CLI 按活跃付款与签名依赖推进

启动时构建活跃操作索引，排除已完成且已核对的终态记录；保留 RemoteSuccess、ExpiredPending 和发送结果未知等待核对状态。SDK 历史仍是校验和恢复的依据。

每次事件唤醒后优先推进待签请求，提交成功后直接取下一请求，直到没有待签、出现重复请求或达到有界批次上限。该过程仍串行签署同一通道；不并发签名、不修改 16 次签名这一协议事实。

不能简单把签名移到全部付款查询之前：TLC 移除签名必须先取得并核验对应的 fulfillment/cancellation 证据。根据当前签名内容查询相关活跃付款，授权成功并落盘后再签名。收款释放在取得可恢复本地 commitment 后尽早推进，仍核验 live funding 和恢复窗口。

常规展示查询和重复全通道余额核对移到批次边界；最终完成前执行完整核对。事件游标先取得再检查状态，防止丢失批次执行期间的更新。

详细设计见 [1.1.2](1.1.2-cli-payment-driver.md)。

### 3. 区分耐久状态与诊断展示

| 状态 | 必须完成耐久写入的边界 |
| --- | --- |
| 付款意图、原 hash、费用、send_started | 首次 send_payment 之前 |
| SDK 授权、签名历史、nonce、恢复证据 | 签名或新 nonce 对外可见之前 |
| 原签名请求与可重放提交参数 | submit_channel_signature 之前 |
| 原像释放授权与 release_started | settle_invoice 之前；SDK/CLI 双层资料分别保留 |
| 完整完成结果 | 报告完成并退出之前 |
| 远端状态、展示文本、心跳时间 | 可合并或仅保留内存；超时/中断输出本次最后一次观察 |

无内容变化不写文件。合并同一批次内非安全边界的付款记录更新；每个安全边界仍同步保存。账户会话未改变时不重复保存 account.json。

第一阶段沿用原文件格式，不进行数据库迁移，不取消 fsync。也不单靠增加线程或把写盘扔到未受管理的后台来掩盖耗时。

### 4. SDK 幂等更新与一次签名一次提交

SDK 的同值授权不增加 revision，也不触发 store CAS。一次签名所需的签名历史、commitment/revocation 恢复证据和下一轮两个 nonce 发布状态，在同一个 CAS 中持久化后统一返回。

已有公开签名 API 保留；HostedSession 使用新增的组合签名路径。PreparedSigning 的版本绑定、nonce 检查和确认时重新校验保持不变；写入失败时不返回签名或新 nonce。

详细设计见 [1.1.1](1.1.1-sdk-durable-signing.md)。

### 5. 测量后的后续候选

本次用户已明确授权签名 RPC 优化，已实现携带既有待签证据的事件/提交响应；它不提供跨付款、余额的一致快照。以下更大范围候选仍保留为后续工作：

| 候选 | 启用依据 | 需要重新设计的边界 |
| --- | --- | --- |
| 合并状态 RPC，返回 channel、signing request、付款证据和 revision | 优化后串行 RPC/actor 路由仍占显著耗时 | 当前 namespace revision 只用于唤醒，并非一致性快照；需要通道 actor 内一致读取与租户权限隔离 |
| SQLite/WAL 或按 key 保存的 durable store | 优化后全量快照序列化/同步写入仍占主导，历史增长明显影响性能 | 现有 signer.bin 迁移、唯一可写后端、崩溃恢复、旧二进制防回退；不能仅把文件换成 DB 就认定 SDK 单 key 历史已消除 |
| 常驻客户端/长连接签名会话 | CLI 启动占比已实测显著，且产品接受改变前台生命周期 | 账户锁、凭证生命周期、后台退出与恢复语义；不在本次保留前台命令的范围内 |
| 缩减协议轮次 | 前述优化完成后仍无法达到目标，成本主要来自协议依赖 | 独立协议与安全设计，不能批量预签未来未知 commitment 或让服务端代签 |

## 风险与依赖

- CLI 签名优先级调整可能重现缺少 preimage 的拒签；必须用实际 TLC 移除请求验证按需授权时序。
- 跨 SDK store 和 payments.json 的写入不是一个事务；保持各自提交边界及原请求恢复方式，不能依赖后台补写。
- 事件游标按 namespace 更新，可能合并多次状态变化；每次唤醒读取当前状态，不能把 revision 当作唯一请求 ID 或假定一事件一签名。
- 历史隔离只保证热路径不逐笔处理完成历史；Book 启动解析、整体文件保存和 SDK 校验历史仍有增长成本，需要单独测量。
- 后续 SDK 组合提交不改变存储版本，但需同时验证旧 API、旧文件读取及回放；新增行为启用前重新编译 CLI。
- 前置方案的可用成果满足后续依赖；完整技术交付集中在本级验收。阶段切换不逐步要求产品验收。

## 验收条件

适用产品条件见 [一级验收](1-lsp-payment-latency.md#产品验收条件)。本级还要求：

1. 有一个活跃付款且有新待签请求时，CLI 一批次可连续处理多个依赖已满足的请求，不在每次签名之间固定睡眠或执行全部历史查询。
2. 已完成历史付款产生的常规 RPC 和 SDK 重复授权写入次数为零；没有内容变化时，SDK CAS 与本地文件写入次数为零。
3. SDK 新组合签名路径每个新签名最多一次签名状态 CAS，包含必要的下一轮 nonce；CLI 原签名重放资料仍先于网络提交落盘。
4. 安全边界、最后完成核对、结果未知恢复及账户锁验证通过；测试覆盖真实拒签场景和关键中断点。
5. 每阶段均报告 RPC 数量、耐久写入次数和耗时变化，未达到一级目标时说明剩余瓶颈及恢复点。
